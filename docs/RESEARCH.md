# Основания архитектуры

Проверено 2 ноября 2026 года. Исследованы документация zapret/zapret2, исходник `goodbyedpi.c`, параметры запуска и описание релиза GoodbyeDPI 0.2.3rc3. Код сторонних проектов не переносился в код приложения.

| Проект | Подход | Вывод для прототипа |
| --- | --- | --- |
| [zapret](https://github.com/bol-van/zapret) | Манипуляция пакетами и потоками, hostlist, инструменты проверки сети | Брать идею выборочной обработки и предварительной проверки; ветка zapret1 завершила развитие |
| [zapret2](https://github.com/bol-van/zapret2/blob/v1.0.6/docs/readme.md) | nfqws2/winws2 и стратегии на Lua, разные протоколы и платформы | Используется как основной движок 0.2.1; профили и результат проверки выбираются отдельно для каждой сети |
| [GoodbyeDPI](https://github.com/ValdikSS/GoodbyeDPI) | Windows, WinDivert, фрагментация и другие методы воздействия на DPI | Компактный отдельный движок для первого Windows-прототипа |

Из [исходника GoodbyeDPI](https://github.com/ValdikSS/GoodbyeDPI/blob/master/src/goodbyedpi.c) проверены флаги `-e`, `--frag-by-sni`, `--native-frag`, `--reverse-frag`, `--blacklist`. Вместо широких пресетов `-9` используются только явные флаги. Не добавляются перенаправление DNS, глобальное подавление RST, обработка без SNI или блокировка QUIC. Это ограничивает область воздействия, но не доказывает полной изоляции.

В [релизе 0.2.3rc3](https://github.com/ValdikSS/GoodbyeDPI/releases/tag/0.2.3rc3) прямо отмечена проблема работы hostlist при включённом Kyber. Она отображается в приложении и ограничивает обещания о точности выборочной обработки. Хеш архива фиксирует полученную копию, но не заменяет подпись автора.

По [документации zapret](https://github.com/bol-van/zapret/blob/master/docs/readme.en.md#when-it-will-not-work), такие методы не являются универсальным решением при подмене DNS, блокировке IP и полноценной реконструкции TCP. Поэтому интерфейс показывает результат HTTP-проверки, а не утверждает, что блокировка доказана или устранена.

[Telegram описывает](https://core.telegram.org/mtproto/transports) TCP, WebSocket и HTTP(S) как отдельные транспорты MTProto. Разбиение TLS не означает обработку обычного MTProto. [Discord указывает](https://support.discord.com/hc/en-us/articles/115001310031-Voice-Connection-Errors) необходимость UDP для голосовых соединений. Это отдельная задача для будущего TCP/UDP-адаптера.

Стартовые доменные наборы редактируемы и не являются полными официальными allowlist. Для них проверяются главные HTTPS-страницы, а CDN не оцениваются по отсутствию ответа у корневого домена. Полная проверка функций требует действий в самих приложениях.

Для окончания процесса при аварии использован [Windows Job Object](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) с `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. Привязка выполняется сразу после запуска процесса. Проверки подтверждают завершение уже привязанного процесса при смерти родителя; существует короткое окно между созданием процесса и его привязкой.

В версии 0.2.1 добавлен адаптер winws2 1.0.6. В текущем подключении профиль `z-fake-md5` дал HTTPS 200 у Discord и YouTube. В отдельном Edge через локальный прокси проверено воспроизведение одного короткого видео YouTube. Для Telegram и ChatGPT предусмотрены разрешённые пользователем выборочные внешние SOCKS5-маршруты. Нативный MTProto, голос Discord, функции аккаунтов ChatGPT и работа у каждого из четырёх провайдеров остаются неподтверждёнными.

Физический интерфейс привязывается к каждому исходящему IPv4-сокету через `IP_UNICAST_IF` и локальный IPv4-адрес. Системные маршруты и работающий Happ не меняются. Режим «Маршрут Windows» такой изоляции не обеспечивает. DNS прямых соединений использует системный резолвер, а SOCKS5 передаёт имя внешнему узлу. Проверки HTTP во время сеанса проходят через тот же CONNECT-прокси, что и отдельный браузер.

Для Telegram Desktop возможна отдельная настройка локального SOCKS5; [официальный формат ссылки](https://core.telegram.org/api/links#proxy-links) — `tg://socks?server=127.0.0.1&port=18080`. Наличие такого маршрута само по себе не подтверждает, что внешний узел пропускает MTProto.

В 0.3.0 реализован локальный MTProxy для Telegram Desktop. Секрет локального прокси используется только для внешнего слоя обфускации. Слой MTProto аккаунта не изменяется. На стороне официального дата-центра используется [документированный WSS-транспорт](https://core.telegram.org/mtproto/transports), с [обфускацией](https://core.telegram.org/mtproto/mtproto-transports#transport-obfuscation). Проверка через весь мост получила resPQ с правильным nonce; AES-CTR проверен по вектору NIST. Это не проверка входа или сообщений аккаунта.

Для Discord добавлены отдельная проверка [Gateway Hello](https://docs.discord.com/developers/events/gateway) и UDP-профиль по сигнатуре [IP discovery](https://docs.discord.com/developers/topics/voice-connections#ip-discovery). Generic STUN не включён, чтобы не обрабатывать другие голосовые приложения. Успех Gateway не подтверждает голос.

Обычный браузер подключается через выборочный системный PAC, установленный через WinINet. Реальный тест Edge подтвердил выбор домена и восстановление прежних настроек; отдельный тест принудительно завершил владельца и подтвердил восстановление наблюдателем. Настройки других приложений не заменяются без проверки владения.
